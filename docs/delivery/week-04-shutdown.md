# Week 4 第四节：优雅停止与重启恢复

## 停止顺序

1. 收到 SIGTERM 或 SIGINT 后设置停止标记，并建立一个所有消费者共用的收尾截止时间。WORKER_SHUTDOWN_TIMEOUT_SECONDS 默认 30 秒，必须为正整数；重复信号不会延长截止时间。
2. 不再发起新的阻塞消费或领取。若信号到达时 BLPOP 正在返回消息，消息通过 LPUSH 归还队首；若领取事务尚未提交则回滚后归还。已提交领取、但尚未启动执行的任务以 WORKER_SHUTDOWN 标记 FAILED。
3. 已经执行的任务继续收尾。期限内提交结果的任务保留 SUCCESS / PARTIAL_SUCCESS / FAILED 等实际终态，不被停止逻辑覆盖。
4. 共用收尾期限到达后，停止仍在执行的子进程，最多等待 1 秒，必要时强制结束并回收，随后将未完成任务标记 FAILED，记录 WORKER_SHUTDOWN_TIMEOUT 和文件级错误。
5. 所有消费者退出后服务才结束。正常停止无遗留的 RUNNING 任务，子进程、文件和数据库连接均已释放；已提交批次保留，未提交事务由连接关闭回滚。

单任务超时与停止期限同时生效，使用先到的期限。收尾时间是给任务完成的时间，之后还需进程回收和最终数据库写入时间。任务子进程使用独立会话，终端 SIGINT 不会绕过父进程收尾逻辑直接中断整个任务组。

## Docker 停止窗口

- WORKER_SHUTDOWN_TIMEOUT_SECONDS=30：应用收尾期限。
- WORKER_STOP_GRACE_SECONDS=45：Docker 强制停止前的总等待时间。
- 调高应用收尾时间时，Docker 窗口也应同步增加，至少留出额外 15 秒用于清理和最终状态写入。

Compose 的 Worker 和隔离测试服务启用 `init: true`，用于转发信号和回收孤儿进程。未修改用户现有 `.env`；新增配置已写入 `.env.example`，未配置 Docker 窗口时使用默认 45 秒。

## 父进程异常退出

父进程为每个任务子进程持有一条专用管道。子进程中的守护线程等待管道关闭；父进程发生 SIGKILL 或异常退出后，管道 EOF 触发子进程立即退出，即使主线程正阻塞读取文件，也会释放文件和数据库连接。正常结束时仍由父进程等待并回收子进程。

SIGKILL 无法执行数据库收尾。因此父进程崩溃后，任务可能暂时保留 RUNNING / CANCELING；下一次恢复扫描按下面的超时规则收敛，不立即重放已执行的任务。

## 重启恢复策略

消费者启动时以及之后每 30 秒的任务间隙执行恢复扫描，每轮最多 100 条：

- 选择 RUNNING / CANCELING 且开始时间超过 JOB_TIMEOUT_SECONDS 的任务；旧记录没有 started_at 时使用 updated_at。
- 使用 `FOR UPDATE SKIP LOCKED`，跳过正在提交的批次，避免阻塞启动或抢改提交中的任务。后续扫描会再次检查这些记录。
- 在同一事务中将过期任务标记 FAILED，更新结束时间、状态更新时间与原因，写入 WORKER_EXECUTION_EXPIRED 错误明细。
- 保留已有业务记录及统计，不把未处理记录补算为行错误，不自动重新执行。
- 未超时任务、等待任务及终态任务不变；重复扫描不会重复记错误。

任务状态是写入保护：恢复后旧执行者无法提交新的批次；仍存活的监控者发现状态已变会停止子进程。多个服务实例使用一致的 JOB_TIMEOUT_SECONDS，避免较短的配置提前终止其他实例的任务。完整自动重试留到第 5 周。

未超过超时时间的崩溃任务会等待后续扫描；扫描与消费共用循环，所有消费者繁忙时扫描可能延后。PENDING 消息丢失仍沿用第二节的扫描补投机制。

## 数据库故障与可追溯性

若任务已停止但最终状态无法回写，或领取提交确认丢失导致状态不确定，日志保留 job_id 和恢复需求，服务停止时返回非零退出码，不能报告为清理成功。数据库恢复后，超时扫描将遗留任务标记 FAILED。数据库不可写期间无法保证立即修改记录，这一失败路径已明确记录并验证。
