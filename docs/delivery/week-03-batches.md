# Week 3 MySQL 分批写入、统计与最终状态

对应 [Week 3 清单第三节](week-03-checklist.md)。已将第二节的整文件事务替换为 **每批 250 条非空 CSV 数据记录** 的独立事务，无需新增依赖或数据库字段。

## 提交与回滚

1. 完整读取并预检文件，通过编码、表头、行数等文件级校验后才写数据库。CSV 结果保留原始顺序、物理行号和原始字段，合法与非法记录一起按 250 行划分批次，尾批可以少于 250 行。
2. 每批先锁定对应任务行，确认状态和已提交进度；合法数据批量写入 `sync_records`，校验错误写入 `sync_errors`。
3. 该批数据、错误及累计 `total_records / success_records / failed_records` 在同一事务提交。总数为完整预检得到的非空数据记录数，成功数仅包含实际提交的记录；运行中可通过现有详情 API 查看每批更新后的统计。
4. 某批发生数据库错误时，整个批次回滚，之前的已提交批次保留。另开事务记录该批失败结果，再继续下一批；不会尝试重新插入这一批业务数据。
5. 最后一批同时提交最终统计、最终状态和 `finished_at`；之前各批保持 `RUNNING`，结束时间为空。

批次失败时，原本合法的每条数据记录生成一个 `BATCH_WRITE_FAILED` 错误，保留真实起始行号和原始字段，`field_name` 为空。消息包含批次编号、源文件物理行范围、安全的错误类别及 MySQL 错误号，不复制数据库异常原文。原本就有校验错误的行保留原错误码，每行最多一条错误，不重复计数。

数据库的 `UNIQUE(job_id, external_id)` 保持有效；不会使用忽略冲突或覆盖旧值的写法绕过约束。解析器的同任务去重覆盖整个文件，因此跨批次重复仍被识别为 `EXTERNAL_ID_DUPLICATE`。

## 提交确认丢失

成功数与失败数之和同时作为已提交数据记录数。每批写入前在任务行锁内核对预期进度：如果本批进度已经提交，则直接使用已保存的结果，避免因提交响应丢失再次写入或再次计为失败。错误记录事务的提交响应丢失也会通过新连接核对已提交进度。

这只处理当前任务执行中的提交结果不明确，不提供崩溃后自动恢复、消息确认或任务重试。若数据库持续不可用，连错误和失败状态也无法保存，任务可能保留 `RUNNING` 与最后一次已提交进度，需人工核查；不会撤销之前成功的数据。

## 已明确的边界口径

| 情况 | 计数与结果 |
| --- | --- |
| “有效数据行”与上限 | 所有非空 CSV 数据记录都计入总数和 10000 行上限，包括校验失败行；表头和空白行不计入 |
| 一行多个字段错误 | 保留首个校验错误，失败数按数据行统计，不按错误字段数量累加 |
| 行号 | 记录起始物理行，表头为第 1 行，空白行占物理行号；带引号换行字段以起始行定位 |
| 全部行通过校验并成功入库 | `SUCCESS`，总数等于成功数，失败数为 0 |
| 全部行均为校验错误 | `FAILED`，成功数为 0，失败数等于总数 |
| 所有合法行均发生系统写入失败 | `FAILED`，成功数为 0，逐行保存批次错误；校验错误行保留原错误 |
| 部分成功、部分校验或批次写入失败 | 完成全部批次后为 `PARTIAL_SUCCESS`；失败数包含失败批次中的所有行，合法行错误码为 `BATCH_WRITE_FAILED` |
| 文件级错误 | 预检在任何批次写入前完成，故没有已提交批次；总/成功/失败均为 0，任务 `FAILED`，保存一条行号为空的文件错误 |
| 连失败批次的错误明细也无法保存 | 停止处理；若随后能写入任务级错误，则记录 `WORKER_PROCESSING_FAILED` 并标记 `FAILED`，保留已提交成功数，将当前及后续未提交行计为失败；该终止原因由任务级错误说明 |

正常完成后始终满足 `total_records = success_records + failed_records`。运行中成功/失败数只表示已提交批次，剩余未处理数为 `total_records - success_records - failed_records`。最后一批无错误时仍保留之前批次的最近错误摘要。

`PARTIAL_SUCCESS` 的数据库约束、后端模型与筛选、OpenAPI、前端中文名称和颜色沿用第二节实现，本次继续通过回归验证。
